# 技术决策

## 8.27 检索与清洗不新增依赖

食物名称检索仅使用 Python 标准库实现 NFKC、casefold、字符 n-gram Dice 和
Levenshtein 距离。当前固定数据规模为 1677 条，逐条字符串计算足以支撑本地
交互和固定评测，引入 `rank_bm25`、FAISS、ChromaDB、jieba 或 NumPy 不会改善
今天目标中的可解释性与可复现性，反而增加安装、版本和索引维护成本。

四阶段分数和固定排序键直接编码为业务规则。每个候选保留 stage、命中词和
来源，但不携带营养数值；只有用户或规则选中真实数据行后，calculator 才按
“每 100g 数值 × 克重 ÷ 100”计算。

检索 Trace 使用独立 JSONL 文件，不扩展 HealthEvent。Trace 写入属于旁路审计：
失败会返回稳定警告，但不会把已经成功的候选检索改成失败。健康记录保存失败
则仍然禁止展示“记录成功”。

完整上游数据只在本地清洗和使用，不进入 Git。清洗只做转换、裁剪、别名抽取
与质量标记，不修正、补零或猜测异常营养数值。

## 8.30 LangGraph 只替换编排层

- 要解决的问题：原有有限轮次 Loop 已经可以工作，但状态分支、补参、确认和
  后续 P1 流程继续增长时会集中在一个 Runner 中，难以直观看出暂停和恢复位置。
- 候选 A：继续扩展原有 Python Loop。
- 候选 B：使用 LangChain 高层 `create_agent` 和通用 ToolNode。
- 候选 C：使用 LangGraph `StateGraph`，复用现有模型协议和 HealthToolRouter。
- 最终选择：候选 C。
- 原因：可以获得显式节点、条件边、checkpoint 和 interrupt，同时不改变已通过
  测试的工具 Schema、确认令牌、幂等和 JSONL 存储边界。
- 不选 B：通用工具执行节点无法直接表达当前 `needs_clarification`、草稿生成、
  签名确认和确定性领域错误协议，迁移风险高于收益。
- 回退：通过 `AGENT_ORCHESTRATOR=legacy` 保留原 Loop；同一领域测试继续覆盖
  两种编排方式。
- checkpoint：P0 使用 `InMemorySaver`，只保存短期图状态。HealthEvent 和 Trace
  仍使用 JSONL，不把业务事实迁移到 checkpoint。
- 安全约束：生成草稿与 interrupt 分成不同节点；interrupt 恢复后才执行写工具。
  写工具继续校验 confirmation token 并使用幂等键。
- 验证证据：全量 pytest、LangGraph 专项 E2E、固定检索评测和页面开发者证据。

## 9.04 P1 状态继续使用原子 JSON 快照

- 要解决的问题：P1 增加档案、目标版本、提醒状态历史和幂等结果，必须支持跨会话读取、
  安全确认和失败不留下半写状态。
- 候选 A：继续使用 JSON/JSONL；候选 B：迁移 SQLite。
- 对比：SQLite 更适合并发、多用户、索引查询和事务迁移；原子 JSON 快照更容易在当前
  单用户本地作品中检查、演示、删除和回滚，也不会同时迁移已稳定的 HealthEvent JSONL。
- 最终选择：本阶段使用 `healthos_state.json` 原子快照，文件权限 0600，写入经同目录临时
  文件和 `os.replace` 完成。HealthEvent 继续使用独立 JSONL。
- 数据形态：档案为当前快照；目标为不可变版本数组；提醒为当前状态加转换历史；幂等结果
  与业务状态同一次原子提交。
- 已知限制：仅适合本地单进程单用户演示；关闭应用后提醒不会产生系统级通知。
- SQLite 迁移触发条件：多用户、并发写、目标/提醒超过本地展示规模，或需要后台调度器。
  迁移时保留 UUID、版本号、时间戳和幂等键；JSON 文件作为只读回退，校验记录数和摘要后
  才切换写路径。
- 验证证据：P1 工具契约测试、确认前后状态测试、重复确认、令牌篡改、目标版本和提醒状态
  历史测试，以及完整 pytest 回归。

## 9.05 业务状态迁移 SQLite，产品保持本地网页

- 触发原因：业务已经包含档案、版本化目标、健康事实、会话恢复、提醒和幂等结果，
  原子 JSON 快照需要整文件重写，跨实体一致性与按时间查询也开始成为明确限制。
- 产品形态：继续使用本地 Gradio 网页。浏览器提供跨平台 UI，本机进程持有数据库和
  模型密钥，不引入 Electron/Tauri 的安装、升级和系统权限成本。
- 主存储：SQLite 保存所有需要更新、关联和恢复的业务状态；启用事务、外键检查、
  busy timeout 和必要索引。
- JSONL 定位：只追加的 Agent/RAG Trace 与显式导出，不再承担可变业务状态。
- 迁移：启动时和命令行均使用同一个幂等迁移器；旧源文件原样保留，SQLite 事务失败
  时不产生半迁移状态。
- 回滚：迁移验收期可设置 `STORAGE_BACKEND=json`；不采用长期双写，避免两个事实源。
- Prompt：Legacy Runner 与 LangGraph Runner 共用五层 Context Pipeline，防止两条
  编排路径出现不同的档案、目标或工具结果优先级。

## 9.09 记忆控制采用受信任 UI，不新增模型 Tool

- 用户需要知道系统记住了什么，并能逐条遗忘、导出或全部清除。
- 这些操作放在“数据与隐私”页，由受信任服务代码读取 SQLite，不把内部 ID 或完整
  记忆列表交给模型，也不增加第 16 个 Tool。
- 删除和全部清除必须二次确认；删除后同步档案偏好，使后续 Prompt 立即停止使用；
  导出只包含长期记忆，不包含健康事件、API Key、确认令牌或原始对话。
- 全部清除不等于删除账号：健康事实、目标、提醒和对话历史保持不变，避免扩大破坏范围。

## 9.14 首次使用：唯一硬前提是模型 Provider，其余全部给默认值

- 触发原因：在全新 clone、没有 `.env` 的状态下实际走查发现，应用能正常启动、
  页面完整，但对话记录链路整体不可用，界面只回一句“对话功能暂时不可用”，
  既不说明缺什么，也不说明下一步。首次使用者无法独立走到第一次有效结果。
- 准备条件分级（新增功能时按此复查，不得随意上升等级）：
  - 必须由用户提供：`AGENT_PROVIDER_MODE` / `AGENT_API_KEY` / `AGENT_MODEL`。
    这是唯一挡住核心任务的前提，缺失时必须在用户开口之前说明。
  - 可用合理默认值：个人档案（`UserProfile` 默认值）、`APP_TIMEZONE`、
    `STORAGE_BACKEND=sqlite`、`RAG_MODE=lexical`、
    `HEALTH_CONFIRMATION_SECRET`（缺省时使用进程内临时密钥）。
    这些一律不得成为首次使用的必填项。
  - 可稍后补充：健康目标、饮水/运动目标值、飞书提醒通道、LangSmith。
    只在用户真正进入该功能时按需说明，不在首屏堆引导。
- 缺项说明规则：
  - 集中前置。能在运行前判断的缺项，在对应入口页直接说明，不让用户靠反复发送
    和报错去发现。
  - 每条说明必须同时给出：缺什么、为什么挡住任务、具体怎么补、补之前还能做什么。
  - 有依赖顺序的准备项按顺序引导（例：提醒依赖飞书通道；饮食估算依赖
    “填名称份量 → 匹配食物 → 选中候选 → 计算”四步）。
- 失败与重试规则：
  - Provider 已经区分了超时、认证失败、限流、连接失败，UI 必须把这个原因透传给
    用户，不得降级成一句通用的“请稍后再试”。
  - 任何失败或不可用分支都必须保留用户已输入的内容，补齐后可直接重发。
  - 未真正执行的回合不得显示“已完成”。
- 成功后规则：写入成功必须清除草稿态文案，并说明结果去哪里看、怎么改。
  页面上不得同时出现“尚未保存”和“已保存”。
- 导航规则：隐藏的 Tab（如 `HEALTHOS_SHOW_DEVELOPER_UI=false` 时的“运行证据”）
  不得出现在任何导航菜单里，避免点了没有反应的入口。

## 9.15 图片识别只做预填，默认关闭

- 触发原因：图片一直只是输入入口，用户每餐都要手敲食物名称。PRD 从一开始就把
  YOLO 定位成"只帮用户预填候选，不能跳过用户确认、数据检索、热量计算和保存"，
  现在补上这一段，边界照旧。
- 职责边界：检测只写"食物名称"这一个输入框。候选确认、Hybrid RAG 检索、
  确定性营养计算和确认保存四步一步不改，全部仍由用户驱动。
  份量不预填——检测框给不出重量，按框面积估重是编造，宁可留空让用户填。
- 运行时选 ONNX Runtime，不选 ultralytics + torch：
  - 运行时只需 `onnxruntime`（约 50MB），前后处理用 NumPy 自己写，可单测；
  - torch CPU wheel 约 1—2.5GB，会让每次 CI 的 `docker build` 多下载约 2GB，
    20 分钟的 CI 超时扛不住；
  - `ultralytics` 只在 `scripts/prepare_food_detection_model.py` 里导出权重时
    使用，不进 `requirements.txt`。
- 前后处理必须对齐官方实现，两处踩过的坑写在这里：
  - 缩放必须用双线性。最近邻会让分数偏移到足以让阈值附近的检测忽有忽无，
    实测同一张图会多出或少掉一个目标。
  - 必须先在全部 80 类里取 argmax，再筛食物类；反过来只在 10 个食物列里取
    argmax，会把一个高分的 `person` 强行改判成它最像的食物，凭空造出
    "蛋糕 0.4"这种候选。这一条用 `bus.jpg` 与 ultralytics 官方后处理交叉验证过：
    限定食物类时双方都返回空。
- 识别能力的诚实边界：使用 COCO 预训练 yolov8n，不做微调，因此只认得 10 个食物类
  （苹果、香蕉、橙、西兰花、胡萝卜、披萨、三明治、热狗、甜甜圈、蛋糕）。
  米饭、番茄炒蛋等中餐菜品一律识别不到，界面必须直说这一点，不得暗示"识别任意食物"。
  为了让这 10 类都能走通"检测→检索→计算→保存"，食物库补了 5 条（28 → 33），
  并同步重建了 `data/index/` 和 `docs/eval_report.json`；固定评测集的 Recall@3
  与拒答准确率不变。
- 权重与许可：仓库是 MIT，Ultralytics YOLOv8 的代码和预训练权重是 AGPL-3.0。
  因此权重不提交，由 `scripts/prepare_food_detection_model.py` 按固定 Release
  下载并导出到 `runtime/models/`（已忽略），README 单独声明许可差异。
  Dockerfile 不做导出，改由部署时挂载。
- 配置分级：按 §9.14，`MEAL_DETECTION_MODE` 属于第三档，默认 `disabled`，
  缺权重或缺 onnxruntime 都只是少了预填，不挡任何核心任务。
  `available` 必须同时检查开关、权重文件和运行时可导入——只查其中一个，会把
  降级状态报告成正常状态，这是 `knowledge/repository.retrieval_receipt` 已经
  踩过的坑。
- `candidate_source` 语义：名称原样来自检测才记 `model`，用户改过一个字就回到
  `manual`。界面不显示虚构置信度，识别不到时只说"没识别出来，请直接填写"。
- 失败一律回退：检测不可用、权重损坏、推理异常、识别不到，四种情况都退回今天的
  手填链路。`tests/e2e/test_manual_meal_flow.py` 保留一条
  `MEAL_DETECTION_MODE=disabled` 下全链路可用的断言，防止以后把识别做成前置依赖。
- Trace：检测证据单独写 `data/detection_traces.jsonl`，只记图片摘要和字节数，
  不记图片内容、文件名或路径——原图默认不保存，Trace 不该成为绕过这条规则的后门。
  食物标签属于健康数据，不进脱敏的 Agent Trace。

## 9.15b 识别后端改用 VLM；COCO YOLO 降级为离线备选

- 触发原因：§9.15 上线当天实测就翻车了。番茄被识别成"苹果 76%"，米饭被识别成
  "蛋糕"。复盘后确认这不是实现缺陷，而是模型选型错误。
- 根因：**COCO 80 类里没有番茄、米饭、鸡蛋、面条、豆腐、饺子**，一个中餐食材
  都没有。而 YOLO 是闭集分类器，**没有"我不认识"这个输出**，必须从 80 类里挑
  一个最像的。所以它不是"识别不到"，而是自信地给错答案——76% 是"在这 80 类里
  最像 apple"的把握，不是"这是苹果"的把握。
- §9.15 写的"中餐菜品识别不到"这句话是错的，实际行为是识别成别的东西。
  这比识别不到更糟：识别不到用户会自己填，识别错了用户可能直接存下去。
  边界描述必须写实际行为，不能写一厢情愿的行为。
- 改为 VLM 预填（PRD L135 本来就写了"YOLO/VLM 预填"）：
  - 多模态模型是开放词表，能说出"番茄炒蛋""宫保鸡丁"，也能说"我认不出来"；
  - 通过已有的 OpenAI-compatible Provider 调用，不需要训练、不需要找权重；
  - 适配器设计在这里拿到了回报：`FoodDetector` 协议不变，
    检索、计算、确认、保存一行没动，只多了一个 `vlm_detector.py`。
- **不把本地食物库的 33 个名称塞进 Prompt。** 那等于把开放词表重新变成闭集，
  会精确复现 COCO 的错误：逼模型从已知名字里挑一个最像的。正确做法是让它自由
  说出中文菜名，再交给现有 Hybrid RAG 和拒答门控判断认不认，认不出就回退手填。
  Prompt 里明确写"如果认不出来返回空列表，不要猜一个最像的答案充数"。
- 隐私立场确实变了，必须显式告知，不能静默外发：
  - `vlm` 模式下图片会发送给用户配置的服务商。本机仍不保存原图，但图片出了本机；
  - 图片外发的说明放在 README 隐私章节和「数据与隐私」页，不写进对话区的表头：
    表头每次上传都出现，长段落会挤掉真正要做的四步操作，实测反而没人读；
  - README 隐私章节新增三模式对照表，写明餐食照片可能包含餐厅、家居环境、
    同桌的人等与饮食无关的信息；
  - 默认仍是 `disabled`，开启是用户的显式选择。
- 视觉 Provider 独立配置（`MEAL_DETECTION_VLM_*`），未设置时回退 `AGENT_*`。
  原因：文本模型不一定支持图片输入（例如纯文本的 Provider），这时只需把视觉
  这一路指向别家，不用动对话链路。
- Provider 报错只回错误类型名，不回原始报文——报文可能带密钥片段。
- 保留 onnx 模式而不是删掉：它离线、免费、35ms，对水果和西式快餐确实可用，
  也是"本地优先"这条产品线的备选。但文档和界面必须写明它会把中餐识别成错的东西，
  不能让人以为它通用。

## 9.16 表单校验必须用中文说"缺哪一格"，不能露出组件层报错

- 触发原因：份量没填时点「查看营养估算」，页面右上角弹出三个红色 `Error`，
  内容是 `Value 0 is less than minimum value 0.01.`。用户既看不懂，也不知道
  该去填哪一格，而且一次弹三个。
- 根因：`gr.Number(minimum=0.01)` 的**客户端**校验抢在服务端之前触发。
  后端 `parse_grams` 本来有中文错误，但请求根本没发出去，那条消息永远到不了用户。
- 规则：**组件层不做业务校验**。`minimum`/`maximum` 一律不设，校验集中在
  `calculate_meal_preview`，用中文说清缺什么、在哪填、补完点哪个按钮。
  上限（10000g）仍由 `parse_grams` 把住，只是换成中文提示。
- 缺项要一次说完，不要点一次补一项：候选和份量都没填时提示"还差 2 项：
  1. …；2. …"，而不是先让用户补候选、再让他补份量。
- 份量输入框从 `gr.Number` 换成 `gr.Textbox`：Number 会把空值渲染成 `0`，
  看起来像已经填了；Textbox 空就是空，placeholder 还能示范格式（"例如 150"）。
  数值解析本来就由 `parse_grams` 负责，不依赖组件类型。
- 对话区的文案要短。四步操作说明和缺项说明都压到两行以内；环境变量、许可、
  隐私这类背景信息放 README 和「数据与隐私」页，不占每次上传都会出现的版面。
- 候选下拉按实测收紧：未处理时是标签 20px + 间距 10px + 控件 48px = 78px，
  下面空一大块；收紧后 68px。改 CSS 前先量 DOM，不要凭截图猜选择器。

## 9.17 餐食记录压到两次点击；匹配与试算不再由用户按按钮触发

- 触发原因：实际使用反馈"步骤太繁琐，用户可能就不想记录了"。原流程上传之后
  还要：填份量 → 点「匹配食物」→ 展开下拉选候选 → 点「查看营养估算」→
  点「确认保存」，四次点击加一次打字。记一餐的成本高到会劝退记录本身，
  而这个产品的全部价值建立在用户愿意持续记录上。
- 判断：这五步里只有两步是用户真正要做的决定——**吃的是什么、吃了多少**。
  「匹配食物」和「查看营养估算」是系统的内部动作，不该由用户按按钮驱动。
- 改动：名称、候选、份量任意一项变化都重跑同一个编排函数
  `refresh_meal_panel`，自动匹配并试算。两个按钮删除。
  上传之后变成：点一个份量快捷按钮 → 点「保存这一餐」，两次点击。
