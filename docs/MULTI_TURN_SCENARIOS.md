# 连续健康管理对话场景与验收

这里的“多轮”不是单纯补齐一个工具参数，而是围绕用户数小时、数天或一个健康周期中的
真实任务持续服务。场景层负责保持主题、选择下一步和控制节奏；底层工具继续负责事实、
计算、确认、安全与持久化。

## 运行机制

每次模型调用前，系统从本轮输入和最近六条用户消息识别当前业务场景，并把对应场景协议
装载到系统上下文。明确的新主题优先于旧场景；“那今晚呢”“接下来怎么做”等省略式追问
会继承最近主题；紧急症状始终覆盖其他场景。

场景协议只影响对话组织，不能绕过以下边界：

- 健康事实只来自已经确认的记录和工具结果；
- 一般健康建议必须检索可信知识并展示来源；
- 写入、目标、偏好和提醒必须经过草稿与确认；
- 不诊断、不猜测趋势原因，不把缺少记录等同于用户没有完成；
- 急症信号立即进入安全分流，不继续普通健康建议。

## 十类核心场景

### 1. 一日饮食连续记录

典型过程：早餐记录并确认 → 午餐继续记录 → 用户询问“今天吃了什么” → 只汇总两顿已
确认餐食 → 用户补充晚餐。每顿饭独立匹配食物和份量，不能沿用上一餐参数；系统不会在
用户只想记录时强行评价饮食。

主要工具：`retrieve_nutrition_candidates`、`calculate_nutrition`、
`prepare_health_event`、`get_health_events`。

### 2. 体重目标陪伴与平台期复盘

典型过程：用户建立减重目标 → 持续记录体重 → 询问平台期 → 系统先读取 14/30 天事实和
当前目标 → 说明数据缺口 → 邀请用户补充近期生活变化 → 用户决定后再调整目标。短期体重
波动不会被解释为脂肪增减，用户补充的原因也不会伪装成数据结论。

主要工具：`get_period_summary`、`get_health_goals`、`prepare_goal_change`。

### 3. 运动计划、完成反馈与恢复

典型过程：建立运动目标 → 记录一次训练 → 用户反馈训练后酸痛或疲劳 → 系统区分已记录
运动与主观感受 → 检索一般恢复知识 → 询问用户是否希望调整下次行动。出现胸痛、呼吸困难
等信号时立即切换安全分流。

主要工具：`get_health_events`、`get_health_goals`、`retrieve_health_knowledge`、
`prepare_goal_change`。

### 4. 睡眠与疲劳改善

典型过程：用户描述连续睡不好 → 系统询问持续时间和白天影响 → 检索可信睡眠知识 → 用户
选择一项今晚愿意尝试的行动 → 经确认创建作息提醒 → 后续询问实际体验并按用户意愿调整。

当前版本没有结构化睡眠事件，因此系统不会声称保存了睡眠时长或质量；睡眠场景使用对话、
可信知识和提醒能力，不伪造尚未具备的数据能力。

主要工具：`retrieve_health_knowledge`、`create_reminder_draft`。

### 5. 7/14/30 天周期健康复盘

典型过程：用户选择周期 → 系统汇总已确认事实、完整度和目标差距 → 区分“观察到的变化”与
“无法从记录得出的原因” → 用户补充主观感受 → 双方选择下一周期的一项行动。任何目标或
提醒变更仍要再次确认。

主要工具：`get_period_summary`、`get_health_goals`、`prepare_goal_change`。

### 6. 健康习惯建立与未完成跟进

典型过程：用户说总忘记喝水 → 系统询问最容易执行的时间点，而不是指责 → 用户选择每天
上午十点 → 生成提醒草稿 → 用户确认 → 后续没有记录时先询问是否忘记记录，而不是认定没有
完成 → 用户可延后、暂停或调整提醒。

主要工具：`get_daily_summary`、`get_period_summary`、`create_reminder_draft`、
`list_or_cancel_reminders`。

### 7. 当日餐食衔接与下一餐建议

典型过程：用户记录早餐和午餐 → 询问“晚餐怎么搭配” → 系统先读取当日已确认餐食和已确认
忌口 → 检索一般健康饮食知识 → 给出少量可替换选择，并说明记录不完整时建议的局限。不会
仅凭一顿饭诊断营养问题。

主要工具：`get_health_events`、`get_daily_summary`、`get_user_profile`、
`retrieve_health_knowledge`。

### 8. 异常症状与安全分流

典型过程：普通运动讨论中用户突然说胸痛或呼吸困难 → 场景立即切换 → 停止训练、饮食和目标
建议 → 提醒联系当地急救或尽快就医。紧急流程不等待用户补齐普通记录字段，也不会评价严重
程度或给出诊断。

主要工具：`retrieve_health_knowledge` 的安全拒答路径。

### 9. 饮食偏好与长期个性化

典型过程：用户说“不吃花生” → 系统先确认这是本次要求还是希望长期记住 → 生成档案草稿 →
确认后写入 → 后续晚餐建议先读取档案并避开花生 → 用户可随时纠正或遗忘。对话中的模型猜测
不会自动成为长期偏好。

主要工具：`get_user_profile`、`prepare_profile_update`。

### 10. 健康目标冲突与优先级协商

典型过程：用户既想减重又想增肌 → 系统先读取现有目标 → 询问当前优先结果、时间范围和可
投入程度 → 用户选择先减重 → 生成一个可核对的阶段目标 → 确认后保留为新版本。系统不会替
用户决定目标，也不会承诺结果。

主要工具：`get_health_goals`、`prepare_goal_change`。

## 自动化验收

- `tests/unit/test_conversation_scenarios.py`：10 类场景识别、安全优先级、主题继承、场景协议
  注入及工具白名单一致性；
- `tests/e2e/test_health_management_conversations.py`：周期复盘后继续讨论、习惯转提醒、睡眠
  转作息提醒、偏好影响后续餐食建议、冲突目标协商、急症中断普通建议、体重平台期和运动
  恢复共 8 条连续业务流程；
- `tests/e2e/test_langgraph_health_flows.py`：跨轮补参、草稿修订、文本确认/取消和保存后查询；
- `tests/browser/healthos.test.cjs`：刷新恢复、历史会话切换和移动端关键路径。

这些测试共同验证：场景可以连续，但事实边界、用户确认、数据隔离和安全规则不会随对话轮次
变弱。
